# 辅导员/班主任批量导入改造方案

> 目标：在**班级管理**模块内提供辅导员与班主任的批量导入能力，并使其成为这两类人员数据的**唯一来源**；学生名册不再手填班主任/辅导员，改由班级关联自动派生；人员变化按既定口径同步到**用户管理**（账号、角色、带班、停用）。

## 0. 结论摘要

| 项 | 结论 |
| --- | --- |
| 档案落点 | 教师档案即账号，落在 `users` 表，不新建 `teachers` 表（无双写） |
| 唯一标识 | **工号 = 登录账号 = `users.username`**（3-20 位字母/数字/下划线） |
| 身份表达 | 人-角色用 `userRoles`（`counselor` / `headTeacher`）；人-班级-身份用 `classCounselors.roleType` |
| 班级关联 | `classCounselors` 增列 `roleType`，主键改为 `(classId, userId, roleType)`，现存数据一律迁移为 `counselor` |
| 离职口径 | `users.disabled = 1` **且**清空该人全部 `classCounselors` **且**清空 `userRoles`，账号保留用于审计 |
| 学生名册 | 模板移除「班主任」「辅导员」两列，两字段改为**按班级派生回填**的历史冗余列 |
| 用户管理 | `/users/import` 拒绝导入 `counselor` / `headTeacher` 两类角色，避免与唯一来源双写 |
| 幂等口径 | 以工号为键逐字段比对，相同则跳过；单次请求事务原子，失败行不写入、可导出明细 |

已确认的实施边界：**本轮只交付方案文档，不改代码**。文末给出分阶段落地计划。

## 1. 现状盘点

### 1.1 现有数据结构

```
users(id, username, displayName, role, passwordHash, mustChangePassword, disabled, createdAt)
roles(key, name, permissions, ownerModules)          -- 内置：admin / counselor / headTeacher
userRoles(userId, roleKey)                            -- 多角色，权限取并集
grades(id, name UNIQUE)
classes(id, gradeId, name, createdAt, UNIQUE(gradeId, name))
classCounselors(classId, userId) PK(classId, userId)  -- ❌ 不区分辅导员 / 班主任
students(... headTeacher TEXT, counselor TEXT ...)    -- ❌ 自由文本，与账号无关联
```

### 1.2 三个必须解决的问题

1. **同一张关联表无法区分身份**：`classCounselors` 只有 `(classId, userId)`。某人既是「电商2601 的辅导员」又是「会计2601 的班主任」时无法表达，班级列表也聚合不出「班主任」列。
2. **学生表的班主任/辅导员是自由文本**：
   - `src/utils/studentImport.ts:221` 从 Excel 取「班主任」原样入库；
   - `server/lib/studentDiff.js:51` 硬编码兜底 `counselor: text(data?.counselor) || '王老师'`，`src/utils/studentImport.ts:284` 也有同样默认值；
   - 结果是学生表里的责任人可以填任何字，与班级、账号三方不一致，且给新数据塞了假的「王老师」。
3. **通道职责重叠**：`/users/import`（用户管理）目前是**纯追加**且允许任意角色，与"班级管理为唯一来源"冲突，必然导致双写与口径漂移。

### 1.3 受影响代码点（已全量核实）

| 位置 | 用途 | 改造要求 |
| --- | --- | --- |
| `server/lib/db.js:88` | 建表 `classCounselors` | 改 DDL + 幂等迁移 |
| `server/routes/classes.js:16,17` | `counselorCount` / `counselorNames` 聚合 | 按 `roleType='counselor'` 过滤；新增 `headTeacherNames` |
| `server/routes/classes.js:124` | 删班清理关联 | 不受主键变化影响，保持 |
| `server/routes/classes.js:193,220,225,228` | 班级导入的辅导员差集写入 | **必须显式写 `roleType='counselor'`**，否则 NOT NULL 默认值会掩盖语义 |
| `server/routes/users.js:68,76,94,96,311,396` | 用户详情/编辑/删除/导入的班级读写 | `setClassCounselors` 需携带 `roleType`（默认 `counselor`）；删除时级联不变 |
| `server/lib/scope.js:18,29,45,53` | 数据权限（带班收口） | 语义不变（按 `userId`），建议加 `DISTINCT` 防重复膨胀 |

| `tests/classesImport.test.js:26` | 班级导入测试断言 | 补 `roleType` 断言与班主任场景 |

## 2. 数据模型调整

### 2.1 目标模型

```
users ──1:N── userRoles ──N:1── roles          （人的系统身份：counselor / headTeacher / 其他）
  │
  └──1:N── classCounselors ──N:1── classes      （人在某班的身份：roleType = counselor | headTeacher）
                                    │
classes ──1:N── students                        （学生的 headTeacher / counselor 由此派生）
```

**唯一来源口径**：人本身的属性（姓名、工号、手机号、在职状态、角色）以 `users`+`userRoles` 为准；人与班级的归属关系以 `classCounselors` 为准。二者都只能通过**班级管理 → 教师名单**（或用户管理的账号维护）写入，不存在第二份教师档案。

### 2.2 `classCounselors` 迁移（SQLite 需重建表）

SQLite 不支持改主键，按官方 12 步套路重建。**关键：重建期间必须关闭外键**，否则 `foreign_keys=ON` 下 `DROP/RENAME` 会让引用表指向旧名或触发级联误删。

```sql
-- 迁移脚本（在 server/lib/db.js 内幂等执行，或 scripts/migrate-teacher-source.cjs 手动执行）
PRAGMA foreign_keys = OFF;                      -- ⚠️ 必须先关，且不能在事务内切换

BEGIN IMMEDIATE;

-- 1) 新结构（PK 含 roleType，历史行默认 counselor）
CREATE TABLE classCounselors_new (
  classId   INTEGER NOT NULL REFERENCES classes(id) ON DELETE CASCADE,
  userId    INTEGER NOT NULL REFERENCES users(id)   ON DELETE CASCADE,
  roleType  TEXT    NOT NULL DEFAULT 'counselor' CHECK (roleType IN ('counselor','headTeacher')),
  createdAt TEXT,
  PRIMARY KEY (classId, userId, roleType)
);

-- 2) 迁移历史数据：现有带班关系一律视为辅导员
INSERT INTO classCounselors_new (classId, userId, roleType)
  SELECT classId, userId, 'counselor' FROM classCounselors;

DROP TABLE classCounselors;
ALTER TABLE classCounselors_new RENAME TO classCounselors;

CREATE INDEX idx_cc_user ON classCounselors(userId, roleType);
CREATE INDEX idx_cc_role ON classCounselors(roleType);

COMMIT;

PRAGMA foreign_keys = ON;
PRAGMA foreign_key_check;                       -- 必须返回 0 行，否则回滚
```

幂等判定：`PRAGMA table_info(classCounselors)` 若已含 `roleType` 列则整段跳过。
回滚：迁移前由数据管理生成快照包；`PRAGMA foreign_key_check` 非 0 或任一语句异常即 `ROLLBACK` 并中止启动。

> **历史语义说明**：现存关联全部标为 `counselor` 是有意选择 —— 历史上只有「辅导员」这个角色在走带班权限（`canManageStudent`、`rosterScope` 都按 `userId` 判定）。若把历史行错判成 `headTeacher`，会导致带班辅导员的编辑权被误收。已有班主任数据的学校需执行第 6 节的半自动补全脚本。

### 2.3 `users` 表增列

```sql
ALTER TABLE users ADD COLUMN mobile TEXT;         -- 选填，11 位手机号；身份核对与导出用
ALTER TABLE users ADD COLUMN teacherSource TEXT;  -- 'import' | 'manual' | NULL；来源通道（审计与回滚用）
```

- 不加「入职/离职时间」：离职状态以 `disabled` 表达，关键动作另有 `accessLogs` 全量留痕，避免冗余状态机。
- 不新增 `employeeNo`：工号即 `username`（已确认），语义单一，天然唯一。

### 2.4 `students.headTeacher / counselor` 转为派生冗余列

- 保留物理列（导出/历史留档/旧查询不受影响），但**语义改为只读派生值**：
  - `counselor` = 该班 `roleType='counselor'` 的教师姓名，按 `users.id` 升序、`、` 连接；无人则 `NULL`；
  - `headTeacher` = 同上，`roleType='headTeacher'`；
- 排序必须稳定（按 `users.id`），否则同一份数据两次导入会产生假 diff（正是当前 `diffStudentFields` 会误判「有变化」的坑）。
- **删除硬编码默认值**：`server/lib/studentDiff.js:51`、`src/utils/studentImport.ts:284` 的 `|| '王老师'` 必须去除。

## 3. 唯一标识与字段映射

| 模板列 | 数据落点 | 必填 | 说明 |
| --- | --- | --- | --- |
| 工号 | `users.username`（唯一标识） | ✅ | 3-20 位字母/数字/下划线；同时作为登录账号与初始密码后缀 |
| 姓名 | `users.displayName` | ✅ | 1-20 字 |
| 手机号 | `users.mobile` | 选填 | 11 位手机号（复用 `normalizePhoneInput` 清洗规则） |
| 人员类型 | `userRoles` + `classCounselors.roleType` | ✅ | `辅导员` / `班主任`，可填「辅导员、班主任」双身份 |
| 所辖班级 | `classCounselors` | ✅ | 多个用「、」分隔；跨年级同名须写「2026级·计应2601」 |
| 在职状态 | `users.disabled` | 选填 | `在职` / `离职`；留空默认在职 |

**映射规则**

```
工号 ──► users.username ──► 幂等键
姓名 ──► users.displayName
手机号 ──► users.mobile
人员类型 ──► userRoles(counselor|headTeacher)  +  classCounselors.roleType
所辖班级 ──► classCounselors(classId, userId, roleType)
在职状态 ──► users.disabled(0|1)
初始密码 ──► "Hzpt@" + 工号（与既有 IMPORT_PASSWORD_PREFIX 规则一致，mustChangePassword=1）
```

## 5. 处理流程

### 5.1 教师批量导入主流程

```
上传 Excel
  └─► 前端解析 + 本地预检（必填/格式/字典/本批重复）──── 预检失败：预览失败明细，阻断提交
        └─► POST /classes/teachers/import
              ├─ 服务端逐行兜底校验 ──── 失败行记入 failures，不参与写入
              ├─ 构造 Target：档案字段 + 角色集合 + (班级 × roleType) 集合
              ├─ 工号不存在 ──► 新建账号（Hzpt@工号、mustChangePassword=1、role=首个身份）
              ├─ 工号已存在 ──► 绑定已有账号
              │     ├─ 是 admin 或当前登录者 ──► 判失败（本通道不可改写管理账号）
              │     └─ 否 ──► 逐字段 diff：无变化 → skippedCount++；有变化 → 仅更新差异字段
              ├─ 在职 ──► disabled=0，userRoles 并集增量，带班差集增量加入
              ├─ 离职 ──► disabled=1 + 清空 classCounselors + 清空 userRoles
              └─ BEGIN IMMEDIATE 事务统一写入 ── 异常 ROLLBACK（全量回滚）；成功写 accessLogs
```

### 5.2 两条导入通道的管辖边界（避免互相覆盖）

| 通道 | 主视角 | 带班写语义 | 冲突处理 |
| --- | --- | --- | --- |
| 班级导入 `/classes/import` | 以**班级**为准 | **覆盖**：文件中该班的辅导员/班主任集合即最终结果 | 同批内同一 (班级,身份) 重复 → 判失败 |
| 教师导入 `/classes/teachers/import` | 以**人**为准 | **增量加入**：不清空该人未提及的其他班级 | 同批内同一工号重复 → 判失败；同 (班级,身份) 重复合并去重 |

> 理由：班级导入的既有行为就是覆盖（当前 `diffCounselorIds` 按差集清人），不能改；若教师导入也按人覆盖，两通道会互相擦除。增量语义更安全，清空场景走「离职」或 UI 单条编辑。

### 5.3 与学生名册的联动

```
学生导入（不再读班主任/辅导员列）
   └─► resolveStudentClassId() 得到 classId
         └─► deriveTeachers(classId) → { counselorNames, headTeacherNames }   // users.id 升序拼「、」
               └─► 写入 students.counselor / students.headTeacher
```

- 班级侧教师变动后**回填存量学生**：抽公共函数 `server/lib/teacherSync.js::refillStudentsByClass(classIds)`，在教师导入事务尾部与班级导入事务尾部各调用一次（事务内执行，保持原子性）。
- 学生单条新增/编辑接口不再接受这两字段；编辑表单改为只读展示。

### 5.4 与用户管理的同步规则

| 场景 | 动作 |
| --- | --- |
| 工号不存在 | 新建账号：`username=工号`、`role=首个身份`、初始密码 `Hzpt@工号`、`mustChangePassword=1`、`teacherSource='import'` |
| 工号已存在 | 绑定复用：`displayName`/`mobile` 有差异则更新；`disabled=1` 且本次在职 → 重新启用 |
| 身份新增（如原辅导员兼任班主任） | `userRoles` 增量补 `headTeacher`（`INSERT OR IGNORE`）；`classCounselors` 以 `roleType` 维度增量 |
| 身份移除（文件中不再出现该身份） | **教师导入不主动回收**（人视角增量语义）；仅当「离职」才全量回收。跨班回收走班级导入的覆盖语义 |
| 离职（在职状态=离职） | `disabled=1`、清空该人 `classCounselors`、清空 `userRoles`（保留账号与审计线索）；若该人是 admin 拒绝执行 |
| 管理员保护 | 工号命中 `role='admin'` 或当前登录者 → 该行判失败，不做任何写操作 |

## 6. 历史数据补全 / 迁移方案

分三层，均幂等、可重复执行：

1. **结构迁移**（启动时自动）：2.2 节 SQL，历史关联全部标 `roleType='counselor'`。
2. **学生表文本回填**（`scripts/refill-student-teachers.cjs`，一次性手动执行）：
   ```sql
   -- 对每个班派生责任人并回填（示意；脚本按班循环 + 参数化）
   UPDATE students SET counselor = (
     SELECT GROUP_CONCAT(u.displayName, '、') FROM classCounselors cc
       JOIN users u ON u.id = cc.userId
      WHERE cc.classId = students.classId AND cc.roleType = 'counselor'
   ) WHERE classId IS NOT NULL;
   -- headTeacher 同理
   ```
   执行前由数据管理生成快照包；执行后输出每个班的回填计数，班级无责任人时置 `NULL` 而非保留旧文本。
3. **人工核对清单**（脚本输出 CSV）：学生表里 `headTeacher/counselor` 与派生值不一致的历史行，列出 `学号/旧值/派生值`，供管理员确认；确因历史任教关系需要保留的，先在班级管理补录对应教师，再重跑脚本。

**回滚方案**：迁移与回填前各做一次数据快照（数据管理模块「恢复前快照」同机制）；结构迁移失败自动 `ROLLBACK`；回填脚本可凭快照整体还原。

## 7. 校验与异常处理

### 7.1 行级校验矩阵

| 校验项 | 规则 | 失败处理 |
| --- | --- | --- |
| 工号 | 必填；`^[a-zA-Z0-9_]{3,20}$`；本批内唯一 | 该行失败，不入库 |
| 姓名 | 必填；1-20 字 | 失败 |
| 手机号 | 选填；复用 `normalizePhoneInput`（去分隔符后 1 开头 11 位） | 失败并回显原值 |
| 人员类型 | 必填；仅「辅导员」「班主任」（顿号分隔双身份）；**不得含 admin** | 失败 |
| 所辖班级 | 必填；逐个匹配班级字典；跨年级同名必须「年级·班级」 | 失败，缺失名单回显 |
| 在职状态 | 选填；仅「在职/离职」 | 失败 |
| 命中管理员 | 工号已是 admin 账号 | 失败："请到用户管理维护管理员" |
| 命中自己 | 当前登录者工号 | 失败（防自锁） |
| 停用管理员 | 离职目标是 admin | 失败："不能停用管理员账号"（与用户管理同口径） |

### 7.2 系统级异常处理

- **全量事务**：校验在事务外完成，写入包 `BEGIN IMMEDIATE`，任一异常 `ROLLBACK`，响应 500「已全部回滚，未产生任何数据变更」。
- **前端预检与服务端兜底同口径**：预检缺字典时跳过该项、由服务端兜底（与现有三个导入通道一致）。
- **同名警告**：不同工号同姓名 → 记入 `warnings`（不阻断），提示人工确认。
- **回填扩散失败**：`refillStudentsByClass` 抛错 → 整个导入事务回滚，教师数据与学生回填保持一致状态。
- **审计**：`logAccess` 记录「导入教师：新增 X、更新 Y、跳过 Z、离职 D、失败 N（含各工号）」，与既有导入同风格。

### 11.3 上线步骤（生产）

1. 数据管理 → 生成「恢复前快照」。

3. 班级管理 → 教师名单：下载模板 → 填入全部辅导员/班主任 → 上传预检 → 确认导入（建议先用「整批模式」跑一次确认无失败行，再放开）。
4. 执行 `node --experimental-sqlite server/scripts/refill-student-teachers.cjs` 看报告与两份清单，确认后加 `--apply` 回填历史学生。
5. 复查学生名册「班主任/辅导员」列与教师名单一致；如需回滚，先恢复快照，再执行 `migrate-teacher-source.cjs --rollback`。

### 11.4 已知边界

- 本通道（人视角）带班写入为**增量**，不会清空某人未被提及的其他班级；跨班清空请用班级导入（覆盖语义）或标记离职。
- 工号即登录账号且唯一：若学校工号与既有 username 体系不一致，需先在用户管理改名或由管理员批量重建账号。
- 手机号仅在「有变化」时更新，留空表示不更新（避免误清空）。
